# Shared Ledger Protocol

Protocol version: `1`

## Purpose

The ledger is the durable communication and coordination system for multiple agents working in one project. It preserves the useful behavior of handoffs: assignment, implementation context, review, correction, questions, suggestions, help requests, evidence, acceptance, rejection, and next action. It replaces repeated narrative handoff files with structured records and Git history.

The ledger does not replace the PRD, ADRs, source code, Git, execution logs, or external systems.

## Truth Model

Use these authorities for different questions:

1. The PRD and approved requirement changes define the desired product.
2. Git and actual external-system state define the current technical state.
3. Verifiable evidence defines what has been tested, deployed, or observed.
4. Phase, work-item, review, request, and evidence records define workflow state.
5. Generated `PROJECT_LEDGER.md` summarizes those records.
6. Actor cursors are resumable bookmarks, not project authority.
7. Logs and archived handoffs provide detail and history, not current status.

When authorities disagree, stop, mark the affected work item `needs_reconciliation`, and resolve the discrepancy without discarding unexplained work.

## Repository Contract

A ledger-enabled repository contains:

```text
AGENT_LEDGER_PROTOCOL.md
PROJECT_LEDGER.md
.project-ledger/
  config.yaml
  requirements.yaml
  phases/
  work-items/
  reviews/
  requests/
  evidence/
  cursors/
```

The root agent instruction file must require all agents to read `AGENT_LEDGER_PROTOCOL.md` and run validation before project work. Add only a pointer to existing agent instruction files; never overwrite unrelated instructions.

## Roles and Capabilities

Agents are actors. Roles are assigned independently on each work item:

- **Owner:** controls objective, scope, dependencies, and task lifecycle.
- **Implementer:** may modify only declared write paths.
- **Reviewer:** reviews an exact commit and owns a separate review record.
- **Integrator:** integrates only after review and dependency requirements pass.
- **Acceptance authority:** accepts a work item or phase after required evidence exists.

Capabilities such as Supabase, Cloudflare, deployment, frontend, or visual testing describe available access. They do not imply ownership. An actor lacking access creates an assistance request for a capable actor.

## Single-Writer Rules

- The work-item owner writes the work-item record.
- Each implementer writes only its own evidence records.
- Each reviewer writes only its own review records.
- The requester owns request intent; the assignee may fill only the response/result fields after accepting the request.
- Each actor writes only its own cursor.
- `PROJECT_LEDGER.md` is generated by the ledger script.
- Source ownership is controlled by each active work item's `scope.write` paths.

Changing ownership requires an explicit ownership-change entry naming requester, approver, previous assignment, new assignment, reason, and scope split. Approval must come from the current owner, integrator, or user. Inactivity alone never transfers ownership.

## Phase Lifecycle

Allowed phase states:

```text
planned -> active -> verification -> accepted
planned|active|verification -> blocked
verification -> rejected
any non-final state -> superseded
```

A phase records its PRD requirements, entry criteria, included and excluded scope, output goals, required and optional work items, acceptance criteria, rejection criteria, current progress, blockers, and acceptance authority.

A phase is not accepted merely because code is merged. All required work items, environment-appropriate evidence, and phase acceptance criteria must pass. Rejection criteria are fail-closed.

## Work-Item Lifecycle

Allowed work-item states:

```text
backlog -> ready -> claimed -> in_progress
in_progress -> blocked|review_requested|needs_reconciliation
review_requested -> changes_requested|ready_to_integrate
changes_requested -> in_progress
ready_to_integrate -> integrating -> integrated
integrated -> verified -> accepted
non-final -> deferred|cancelled
```

Each work item records its phase, PRD requirement IDs, roles, exact Git baseline, branch, write/read-only/forbidden paths, dependencies, objective, approach, outputs, constraints, acceptance criteria, rejection criteria, progress checkpoint, evidence, open communication, residual risk, and next action.

`integrated`, `verified`, `deployed`, and `accepted` are distinct facts. Deployment is recorded as evidence and may be required for verification or acceptance.

## Startup and Resume

At every new chat, resumed session, scheduled check, or task switch:

1. Read the project protocol.
2. Run ledger validation.
3. Read generated project status.
4. Read the current actor's cursor.
5. Inspect the actor inbox.
6. Read the active phase and assigned or requested records.
7. Verify canonical branch, canonical commit, current branch, and worktree status.
8. Reconcile discrepancies before work.
9. Run task preflight before any source mutation.

Chat content is not durable until its relevant decision, question, answer, result, or next action is recorded in the ledger.

## Starting and Switching Work

Before claiming a task, confirm that it is ready, its dependencies permit work, no blocking request is open, and its write scope does not overlap another active task.

Before switching tasks, checkpoint the old task with the current commit or dirty-state explanation, verification result, blocker or skip, residual risk, and exact next action. Release unused scope, update the actor cursor, validate, then claim the new work item.

No task may remain `in_progress` without a meaningful checkpoint.

## Parallel Work

Classify concurrent work as:

- **Isolated:** disjoint write paths and no shared mutable contract.
- **Dependent:** separate write paths with a frozen versioned contract and explicit dependency.
- **Overlapping:** shared write paths or mutable contract; serialize or split before proceeding.

Database migrations, authentication, shared contracts, quota, security policy, and deployment configuration are cross-cutting until proven isolated. A contract change must identify the contract owner, contract commit, affected tasks, and required acknowledgements. Affected work becomes `needs_reconciliation` until rebased or explicitly reconciled.

## Communication Records

Use requests rather than new handoff documents:

- **question:** decision or clarification, blocking or non-blocking.
- **suggestion:** proposed improvement; never changes scope automatically.
- **assistance:** bounded action requiring another actor's capability.
- **blocker:** concrete condition preventing progress.
- **decision:** approved project-level choice that affects active work.

Every request identifies sender, recipient, work item, status, whether it blocks work, requested output, and current result. Assistance never transfers ownership. The assignee performs only the authorized bounded action and records sanitized evidence.

Important updates target actors through `notify`. An actor inbox compares each record's local revision with the actor cursor's seen revision. There is no shared global counter, avoiding parallel revision collisions.

## Review and Correction

An implementation may enter `review_requested` only with an exact head commit, changed-scope summary, evidence, skipped checks, known limitations, and explicit next action.

Reviewers:

1. Review the exact submitted commit.
2. Verify relevant acceptance and rejection criteria.
3. Write findings with stable IDs, severity, location, problem, required outcome, and optional suggested solution.
4. Record one verdict: `approved`, `changes_requested`, `rejected`, or `blocked`.
5. Do not edit implementation while acting only as reviewer.

Corrections update the same work item and produce a new exact commit. Re-review must name that new commit. A prior approval does not apply to later commits.

## Integration and Acceptance

Integration requires satisfied dependencies, an approved review for the exact head commit, a current canonical baseline, no conflicting write ownership, and passing integration checks. Record the integration commit separately from the implementation commit.

Verification requires evidence appropriate to the claimed environment. Local mocks do not prove live deployment. Skipped checks remain explicit gaps.

Acceptance requires the designated authority, all required evidence, no active rejection criterion, and no unresolved blocking request. Never infer acceptance from implementation, merge, or another agent's narrative claim.

## Evidence and Logs

Logs contain full commands, debugging attempts, and detailed output. Evidence records contain durable summaries: command, environment, exact commit, result, pass/fail, skips, artifact pointer, limitations, and safe timestamp.

Never record secrets, credential values, auth headers, cookies, private request bodies, database URLs, signing material, or unsanitized exceptions. A pointer to inaccessible logs is insufficient for critical facts; preserve the sanitized conclusion and reproducible command in evidence.

## Session Checkpoint and Recovery

Before a normal session ends, update meaningful work-item progress, evidence, requests, and the actor cursor, then validate and regenerate the summary.

After an interrupted session, compare the cursor, work-item checkpoint, Git branch, Git status, and recent commits. Mark unexplained divergence `needs_reconciliation`. Never delete, overwrite, commit, or continue another actor's unexplained changes.

## Monitoring

The skill does not watch files or wake agents. The user may schedule each agent to run inbox and status checks. Monitoring must be quiet when nothing actionable changed and must not claim or mutate work unless the relevant record authorizes it.

Notify only on meaningful events: assignment, blocking question, assistance request, contract change, review request, changes requested, dependency completion, integration readiness, failed validation, task blocker, or phase acceptance readiness.

## Historical Documents

Keep existing handoffs as read-only archive during migration. Ordinary transitions use ledger records. Separate documents remain appropriate for ADRs, external audits, release reports, migration runbooks, and postmortems.
